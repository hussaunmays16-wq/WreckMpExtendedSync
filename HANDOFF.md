# WRECKMP EXTENDED SYNC — ПОЛНАЯ ПЕРЕДАЧА ПРОЕКТА ДЛЯ ИИ-ПРЕЕМНИКА

## 1. Что это

Мод для My Summer Car (MSC), расширяющий кооп-мультиплеер WreckMP. Автосинхронизация того, что WreckMP сам не синкает: почта/заказы деталей Теймо, спавн-предметы из чит-бокса, предметы в руках, общий кошелёк, сюжетные деньги (Jouko/килью/Паятсо), телефон/вилка/фонарик, пассажир на мопеде Jonnez (клавиша U).

- **Стек:** C# / .NET 3.5 / Unity 5.0 / MSCLoader / Harmony 1.2 / PlayMaker (игра вся на FSM)
- **Текущая версия:** v3.10.0

## 2. Архитектура мода

- **Harmony-префикс на `PlayMakerFSM.SendEvent`** (`PostalChainPatches.SendEvent_Prefix`) — перехват всех FSM-событий игры; фильтр по кешу корней (`allowedRoots`/`rejectedRoots` HashSet).
- **`SafeFsmWatcher`** — polling-компонент: подписки на FSM-состояния, каждый кадр сравнивает `ActiveStateName`; поддерживает пустой список состояний = «любой переход» (сниффер).
- **Сетевые события** через WreckMP API: `GameEvent`/`GameEventWriter`/`GameEventReader`, `.Send(writer, 0uL, safe: true)`. Все критичные события шлются safe:true (reliable).
- **`FileLogger`** — лог в корень игры `WreckMPExtendedSync.log` (ротация 5МБ, flush 5с, strip RichText-тегов). Плюс Harmony-патч на `ModConsole.Error` пишет все ошибки в файл.
- **Reflection** в приватные поля WreckMP (15+ точек, все сверены с декомпилом — точные имена: `OwnedRigidbody.owner/OwnerID`, `NetRigidbodyManager.RequestOwnership(OwnedRigidbody, ulong)`, `SteamNet.OnLobbyMemberStateUpdate(LobbyChatUpdate_t param)` и др.).
- **`CheatSpawnedItemSync`** — спавн-предметы: registration по строковому ID (`bcb_{steamId}_{name}_{batch}_{i}`), хеш FNV-1a → `NetRigidbodyManager.AddRigidbody`. follow-паттерн для предметов в руках напарника (не парентим к руке — `followTarget` + `TransformPoint` в Update; AUTO-RESCUE при потере цели; `heldByRemoteSteamId` для `OnMemberExit`-спасения).
- **`UniversalHandItemSync`** — визуал-клоны предметов в руках напарника (слой 2, lossyScale-пересчёт, дедупликация против реальных follow-предметов, negative-cache шаблонов).

## 3. Доказанные факты об архитектуре WreckMP (из декомпила, критично!)

1. **Хост симулирует физику ВСЕХ машин, кроме мопеда Jonnez** (исключение захардкожено в `SendEnterDrivingMode`: только для "JONNEZ ES(Clone)" делается `RequestOwnership`). Клиент за рулём = только ввод (`NetVehicle.Owner`), НЕ владелец rigidbody. **Любая попытка передать владение кузовом клиенту = rubberband.** Поэтому наш vehicle-слой удалён целиком в v3.9.0.
2. **`OwnedRigidbody.cachedPosition/cachedEulerAngles` — мёртвый write-only код** (читаются 0 раз в ядре). Наш `UpdateNetRigidbodyCache` — доказуемый no-op (оставлен).
3. **Протоколы (Ctrl+O):** SAFE = все события reliable; FAST = все unreliable; DEFAULT = смесь (физика unreliable). `reqOwnerEvent` в DEFAULT шлётся unreliable → потеря пакета = вечный рассинхрон владения. **Играть только на SAFE.**
4. **Руки:** WreckMP НЕ парентит предметы к кисти. Предмет = `isKinematic=true` + позиция по сети, IK кисти тянется к `grabbedItem.position`. Спавн-предмет с незарегистрированным хешем → `GetRigidbody(0)=null` → рука не позиционируется (наш follow-паттерн это чинит).
5. **`SteamNet.OnLobbyMemberStateUpdate`:** `if (m_ulSteamIDUserChanged == HostID) CoreManager.Disconnect()` — эмулятор Steam генерирует ложные события → хост отключает сам себя. Наш `LobbyDisconnectionGuard` (Harmony, точная сигнатура) блокирует.
6. **Приём пакетов rb:** `if (ownedRigidbodies[hash].OwnerID != packet.sender) continue;` — пакеты не-владельца молча отбрасываются.

## 4. Текущее состояние (v3.9.8) — режим «один владелец заказа»

После 8 итераций (v3.9.1–v3.9.8) почтовый блок приведён к минимализму:

```
Delivery: скип POST_ORDER (ApplySkipLocal: нативный FINISHED + TX DeliveryReady)
          → у получателя: RX (items+price), телефонный звонок
Оплата:   нативный чек инициатора → watcher {CreateItems, Pay} → TX/RX PostOrderPay → деньги у обоих
Unbox:    нативная коробка инициатора → ParcelUnboxTracker/watcher → InitiatorUnboxCoroutine
          → TX/RX CatalogUnbox → деталь материализуется у получателя (HandleCatalogPartUnbox)
Физика коробок: только WreckMP (наша регистрация удалена в v3.9.8)
Чек у получателя: НЕ создаётся
```

Удалено за серию: спавнер коробок (`SpawnMissingOrderBoxes`), `MP_PAY`-инъекция, авто-детект доставки по чеку, `RegisterUnpackedBoxesCoroutine` (перехват физики), `RestorePostOrderBuyVisuals`, clutter purge. Дифф v3.9.7: –377 строк; дифф v3.9.8: –140 строк.

## 5. ЖИВАЯ ПРОБЛЕМА (главная, на момент передачи)

**Коробки заказа спавнятся только у инициатора скипа/заказа, у второго игрока их нет.**

Симптом эволюционировал по итерациям:
- v3.9.4–3.9.6 (наш спавнер у обоих): двойной спавн (94 коробки, завалили магазин), пустые имена в пакете (42/47 null — вероятно смещение потока чтения или ArrayList с null), авто-оплата от MP_PAY.
- v3.9.7+ (нативный путь): коробки только у инициатора — **нативный FINISHED игры спавнит только локально**. Это фундаментальное ограничение: MSC-почта не сетевая, WreckMP её не синкает (PostOrderBuy/коробки не в его sync-реестре).

**Дилемма, которую предстоит решить:**
- **(а)** Вернуть наш спавн у получателя, но ОДИН раз и с dedup (спавнить только по RX CatalogUnbox при первом открытии? или по RX Delivery с guard от двойного вызова — в v3.9.6 двойной вызов был из-за двух точек входа, можно оставить одну);
- **(б)** Не спавнить коробки у получателя вообще — деталь материализуется при открытии инициатором (уже работает! RX CatalogUnbox → HandleCatalogPartUnbox — единственная стабильно зелёная часть цепи);
- **(в)** Выключить блок.

Знание для решения: RX CatalogUnbox-материализация работает у обоих во всех прогонах. Чек-синк (TX/RX PostOrderPay + деньги) работает. Звонок работает. Не работает только «коробки у второго».

## 6. Прочие известные живые баги (меньшего приоритета)

1. **«Синхра отставала от реальности»** — частично лечилось v3.9.8 (удалён конфликт RegisterUnpackedBoxes + NetRigidbodyManager на нативные коробки). Требует подтверждения прогоном.
2. **Конверт заказа материализуется у обоих** (`OnReceiveOrderPlaced` инстанцирует из template) — работает, но position/rotation иногда расходятся.
3. **Money-watch:** одновременные траты обоих → взаимная перезапись абсолютных значений (молчаливая расходимость). Гварды 0.6с смягчают.
4. **Kilju fallback 170 MK** если FSM-переменной Payment нет.
5. **FSM-инъекции** телефона (`MP_PICK`/`MP_CLOSE`) и фонарика (`MP_ON`/`MP_OFF`) — если реальные состояния FSM называются иначе, молча не работают (не проверено рантаймом).
6. **Jouko:** ложное срабатывание возможно в 3с-окне перезагрузки сцены (`isSceneResetting`).
7. **ApplySkipLocal POST_ORDER-петля:** watcher ловит наш FINISHED через кадр; защита — только 2с-дебаунс `lastPostOrderSkipTime`.

## 8. Методология (чтобы не наступить на те же грабли)

1. **Не дублируй игру.** Каждая попытка спавнить/управлять тем, что MSC делает нативно (коробки, чек, физика), заканчивалась войной с игрой. Рабочая стратегия: слушать нативные события → транслировать минимальное событие → применять минимальный эффект у получателя.
2. **Один путь.** Две точки входа в одно действие = двойные вызовы (v3.9.5: спавн из двух мест).
3. **Матчинг по позиции/имени — зло.** У коробок нет сетевых ID; WreckMP синкает rb по хешам, но только для зарегистрированных. Стабильные ID есть только у наших спавн-предметов.
4. **Гварды-флаги (`deliveryArrivedSent` и пр.) ставятся в одном месте, сбрасываются в другом** — после каждой ампутации проверять, не залип ли флаг (болезнь v3.9.7).
5. **Диагностика TX/RX в FileLogger** (первой строкой приёмника) — окупилась полностью: каждый обрыв локализуется одной строкой.
6. **Прогон после каждой правки обязателен** — 60% правок серии вели себя не так, как читалось по коду.
7. **WreckMP владеет физикой.** Наш код не трогает NetRigidbodyManager для игровых объектов (только для собственных спавн-предметов).
8. **Тестовая среда:** два инстанса на одной машине; хост 20-30 FPS — тайминги искажены, гонки проявляются сильнее, чем на двух ПК.
